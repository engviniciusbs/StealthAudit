# Fase 4: diagnóstico PHP limitado

Implementação verificada em WordPress 7.1.4, PHP 8.3.36 e MariaDB 10.11 do ambiente local isolado. Não há endpoint público de diagnóstico. `Runtime::diagnostic_health()` é uma API interna, cuja exposição futura exige autorização.

## Ciclo de coleta e comportamento do site

O loader contém seu próprio handler temporário de bootstrap. O coletor permanente só é registrado em `muplugins_loaded`, prioridade -1000, depois de esse guard ser restaurado, antes dos plugins convencionais. Outros MU plugins executados antes desse hook não são cobertos. Uma instalação existente abre o armazenamento por `Schema::current()` nesse ponto, sem DDL. Se o schema ainda não existe, guarda somente registros reduzidos em memória até `plugins_loaded`, prioridade 5, onde ocorre a inicialização/migração normal. Fatal antes desse ponto na primeira instalação pode perder o buffer; shutdown nunca instala tabelas nem tenta recuperar conexão arbitrariamente.

As assinaturas seguem [D5](../plans/2026-11-07-documentation-discovery.md): callback com quatro argumentos, retorno `mixed`, `error_get_last()` no shutdown. `error_reporting() & severity` governa a captura; `@` é respeitado conforme a máscara efetiva do PHP. Nenhum WP_DEBUG, display_errors, código HTTP, exception handler ou error_log é configurado. Sem handler anterior, retorna false para manter o processamento nativo. Nunca converte warning em exceção.

`set_error_handler()` devolve o callback anterior, **não a máscara de severidades** com que ele foi registrado. Encadear E_ALL poderia chamar um handler NOTICE-only para um WARNING e alterar o site. Se já houver handler, o coletor restaura imediatamente o registro nativo anterior e informa `limited_previous_handler`: não captura nonfatals por esse caminho, preservando máscara, retorno e exceções anteriores. A captura fatal por shutdown continua em melhor esforço. Um plugin que substitua o handler depois pode limitar a cobertura também; nenhum mecanismo impede isso ou promete observar handlers de terceiros.

O `WP_Fatal_Error_Handler` 7.1.4 local foi lido: o template padrão chama `wp_die` com `exit=false`. O teste fatal real deixa o handler do core instalado e prova que o callback posterior do coletor é alcançado nesse ambiente. Drop-ins, callbacks anteriores que chamem exit, encerramento forçado, memória esgotada, falhas de conexão e outros ambientes podem impedir a coleta. Não há leitura de debug.log, logs do servidor ou chamadas arbitrárias de `error_log()`, nem captura de falhas anteriores ao registro. Um fatal pode ser o último erro observado; não há reconstrução de backtrace.

## Privacidade, limites e agregação

O normalizador limita trabalho de texto a 8192 bytes, descarta o sufixo de stack trace nativo antes de buffer/persistência, reduz controles, UTF-8 inválido e padrões conhecidos de credenciais, Bearer, headers Authorization/Cookie, userinfo de URL, blocos PEM e caminhos absolutos. A mensagem final tem até 1024 bytes UTF-8; o arquivo é relativo à raiz WordPress, ASCII seguro, até 255 bytes, ou `external.php`. A linha fica entre 0 e 2147483647. Mensagens arbitrárias ainda podem conter dados sensíveis sem padrões reconhecíveis; esta redução não constitui anonimização completa. As futuras telas precisam escapar os dados na leitura.

O buffer guarda no máximo `min(errors_per_request,20)` ocorrências reduzidas por requisição (padrão 5). Reentrada de normalização/escrita não produz uma cadeia de diagnósticos. Uma falha de backend encerra novas tentativas de escrita desse coletor no request. Não há arquivo de fallback ou contador durável prometido durante falha do banco.

O fingerprint usa gravidade, mensagem reduzida, arquivo relativo e linha. Grupos ocupam buckets UTC fixos de cinco minutos: `first_seen=LEAST(...)`, `last_seen=GREATEST(...)` e incremento atômico de ocorrências, saturado em 2147483647. Um bucket novo cria outra linha. A retenção lógica de 30 dias continua baseada em first_seen, portanto repetições não renovam indefinidamente mensagens antigas.

Cada ocorrência, inclusive UPDATE de grupo, passa pelo mesmo Budget de trabalho, ritmo, capacidade e pending/CAS usado nas inserções, reservando conservadoramente uma linha e todos os bytes. Isso pode atingir os limites antes de a tabela estar fisicamente cheia. A reconciliação limitada existente corrige a sobrecontagem quando não há escritores pendentes; nenhum reembolso é feito pelo coletor. Auditoria e diagnóstico conservam limites separados. Duas primeiras ocorrências concorrentes podem criar dois grupos no mesmo bucket; a soma das ocorrências confirmadas continua representando as escritas, sem promessa de exatamente uma linha por fingerprint/bucket. Uma limpeza concorrente que remova um grupo selecionado pode fazer a atualização retornar false; não há retry ilimitado.

Saúde é local ao request: `disabled`, `waiting_storage`, `available`, `limited_previous_handler`, `limited` e `storage_unavailable`. Dropped/buffered são indicadores limitados em memória, não contadores exatos globais. `available` informa disponibilidade observada, não prova ausência de erros. Capacidade/ritmo/tempo limitados e backend indisponível não são apresentados como uma lista vazia saudável.

## Evidências e limites de teste

`npm run test:unit`, `npm run test:integration` e `npm run quality` usam o ambiente isolado de [setup](local-setup.md). No snapshot final, confirmado por verificação independente: unidade **123 testes / 358 asserts PASS**; integração **29 testes / 232 asserts PASS**; lint PHP, WPCS/PHPCompatibilityWP e PHPStan nível 6 com 512 MiB **PASS**. `git diff --check` também passou. O teste unitário adicional do normalizador foi escrito por um revisor em arquivo separado; as revisões finais de qualidade e anti-patterns passaram.

Os testes unitários cobrem mapeamento de gravidades, caminhos Windows/Unix e fronteira de raiz, máscaras conhecidas, Unicode/cortes, descarte de trace, handler anterior true/false/null/throw, máscara anterior restrita, supressão ativa e recursão durante falha. Os testes de handlers são subprocessos PHP: fatais nunca derrubam o runner PHPUnit.

A integração utiliza tabelas InnoDB com prefixo aleatório e verifica buffer/flush, gravidades, redação, janela/contagem/horários atrasados, retenção lógica, pending, reconciliação, cap/rate, backend ausente e preservação da saúde limitada após uma rejeição seguida de escrita bem-sucedida. O subprocesso fatal carrega WordPress real, mantém o fatal handler do core e persiste uma única ocorrência fatal, sem caminhos absolutos na mensagem. O coletor desse teste é explícito. Não foram validados PHP 8.4/8.5, MySQL alternativo, exaustão de memória ou drop-ins específicos de hospedagem nesta fase.

O smoke independente também exercitou a ligação Runtime real via HTTP no ambiente local: um plugin convencional temporário emitiu um warning após o MU e antes de `plugins_loaded`; foi persistido um único diagnóstico, com mensagem reduzida, arquivo relativo, linha, UTC, occurrences=1 e pending=0. `wp-login.php` continuou respondendo HTTP 200, com formulário preservado e corpo de 6677 bytes, sem warning ou sentinela da fixture. A máscara de erros e a configuração de exibição permaneceram inalteradas, e o painel continuou negado pelos defaults. Plugins, arquivos temporários e artefatos usados no smoke foram removidos. Essa evidência comprova o caminho observado de warning em instalação já inicializada; não amplia a cobertura para falhas anteriores ao registro, fatais em toda hospedagem, primeira instalação sem banco pronto ou handlers/drop-ins de terceiros.
